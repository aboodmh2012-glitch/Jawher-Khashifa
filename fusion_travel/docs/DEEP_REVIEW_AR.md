# تقرير المراجعة والإصلاح العميق — Fusion Travel 19.0.2.5.0

## الخلاصة

النسخة السابقة كانت نسخة دمج أولية، وليست جاهزة للإنتاج. تمت إعادة مراجعة الموديول الحالي في GitHub، والباك إند المدمج، ومسارات الموقع والبوابة، والمحاسبة، والمحفظة، والصلاحيات، وتكامل Amadeus. النسخة الحالية تحافظ على الاسم التقني `fusion_travel` ونماذج/معرّفات النسخة القديمة حتى تعمل كتحديث لنفس الموديول.

## الإصلاحات الحرجة المنفذة

### 1. إغلاق التلاعب عبر RPC

- منع مستخدم السفر من إنشاء حجز بحالة مدفوعة أو بمرجع مورد مزيف.
- حماية حقول السعر والـMarkup والعرض المختار وبيانات التسعير وحالة الدفع ومرجع المورد.
- تحويل دوال عروض البحث وعمليات الموقع الحساسة إلى دوال خاصة غير قابلة للاستدعاء العام عبر RPC.
- التحقق من أن المستخدم الحالي هو مالك الحجز قبل استخدام `sudo()` في مسارات الموقع.

### 2. إصلاح الصلاحيات وتعدد الشركات

- فصل الأدوار إلى Travel User وTravel Accountant وTravel Manager.
- تقييد المستخدم العادي بالحجوزات والتذاكر المسندة إليه أو التي أنشأها.
- منح المحاسب/المدير نطاق الشركة المسموح بها فقط.
- جعل سجلات API للمدير للقراءة فقط، وإنشاؤها/تعديلها داخليًا فقط.
- إضافة فحوص تطابق الشركة والعميل والعملة بين الحجز والفاتورة وأمر البيع والتذكرة.

### 3. حماية دورة حياة الحجز

- منع تغيير الشركة أو العميل أو العملة أو نوع الحجز بعد بدء البيع أو الدفع أو المحاسبة أو معالجة المورد.
- منع تغيير بيانات المسافر والمسارات والفندق/النقل بعد الدفع أو بدء طلب المورد إلا بصلاحيات مناسبة.
- منع نقل مسافر أو مسار أو إقامة أو خدمة مركبة من حجز إلى حجز آخر.
- منع إلغاء الحجز المدفوع أو الذي لديه نشاط عند المورد بمجرد تغيير الحالة.
- منع تأكيد حجز موقع غير مدفوع أو غير مرتبط بطلب مورد مؤكد.

### 4. إصلاح طلبات المورد وAmadeus

- استبدال الاعتماد على مكتبة Python المؤرشفة بعميل REST مباشر.
- إضافة OAuth2 client credentials وتخزين التوكن في ذاكرة العامل فقط.
- إضافة Timeout فعلي من 5 إلى 180 ثانية.
- فرض HTTPS في وضع الإنتاج.
- تنقيح الحقول السرية من السجلات حتى عند تفعيل Debug Logging.
- منع إعادة الإرسال التلقائي عندما تكون نتيجة الطلب الخارجية غير مؤكدة؛ تتحول الحالة إلى `Needs Review`.
- دعم `queuingOfficeId` الاختياري عند تفعيل أكثر من consolidator من Amadeus.
- إصلاح خطأ كان يعيد تسعير الرحلة مرتين في نفس العملية.

### 5. إصلاح المحفظة والمحاسبة

- قفل عمليات المحفظة لنفس العميل/الشركة داخل المعاملة لمنع الصرف المزدوج المتزامن.
- إنشاء قيد تسوية فعلي: مدين التزام المحفظة ودائن ذمم العميل ثم مطابقة الفاتورة.
- عدم اعتبار دفع المحفظة مكتملًا قبل ترحيل القيد ومطابقة الفاتورة.
- منع تعديل أو حذف معاملات المحفظة المرحلة؛ التصحيح يكون بقيد/عملية مقابلة.
- منع حذف القيود والفواتير المرحلة عند إعادة التذكرة للمسودة.

### 6. إصلاح التذاكر والأرباح

- توزيع السعر الأساسي والضرائب والـMarkup على المسافرين حسب `travelerPricings` بدل القسمة العمياء.
- معالجة فروق التقريب في آخر مسافر حتى يتطابق مجموع التذاكر مع عرض المورد.
- تصحيح قيمة استرجاع العميل بحيث تقل الرسوم المحتجزة والغرامة من المبلغ المعاد.
- منع الرجوع إلى المبلغ القديم إذا كانت النتيجة الصريحة للاسترجاع صفرًا عمدًا.
- منع عمولة المورد من تجاوز Fare + Tax.
- رفض إنشاء مستند محاسبي بمبلغ سالب بدل استخدام القيمة المطلقة بصمت.
- ربط Exchange/Refund/Void بالتذكرة الأصلية مع فحص الشركة والعملة.

### 7. تحسين الترقية من الموديول الحالي

- المحافظة على `fusion.travel.flight.ticket` و`fusion.travel.airline` والحقول والعلاقات القديمة.
- المحافظة على معرّفات القوائم والإجراءات والشاشات والصلاحيات القديمة لتحديثها بدل تكرارها.
- تعبئة الشركة من مستندات محاسبية متفقة على شركة واحدة، ثم من شركة منشئ السجل.
- تعليم الحجوزات القديمة التي لديها مرجع مورد أو حالة Booked/Ticketed/Confirmed على أنها منشأة، لمنع إعادة إرسالها.

## نتائج الفحص الساكن

- 26 ملف Python تم تجميعها وتحليلها بنجاح.
- 17 ملف XML تم تحليلها بنجاح.
- 91 معرّف XML تم فحصها دون تكرار.
- 32 صف صلاحيات تم فحصها دون تكرار أو مراجع Models مفقودة.
- 12 Model مخصص تم اكتشافها ومطابقتها مع ACLs.
- جميع ملفات Manifest وAssets موجودة.
- JavaScript اجتاز فحص الصياغة بواسطة Node.js.
- لم يتم العثور على `t-raw` غير آمن أو مفاتيح API مضمنة في الكود.

## إصلاحات متابعة — 19.0.2.5.0

أُغلقت ثلاث ثغرات High اكتُشفت في مراجعة لاحقة على 19.0.2.4.0:

1. **رضيع / نوع المسافر:** إعادة `associatedAdultId` و`travelerType`
   (`ADULT` / `CHILD` / `HELD_INFANT`) في `_build_amadeus_travelers`، مع رفض
   حجوزات فيها رضع أكثر من البالغين.
2. **التحقق قبل خصم المحفظة:** `_ensure_provider_booking_ready()` يتحقق من
   بيانات المسافرين/الضيوف (بما فيها DOB والهاتف والإيميل للطيران) **قبل**
   ترحيل الفاتورة وخصم المحفظة، وفي بداية `_create_provider_order` أيضاً.
3. **تسعير الفندق:** عند عدم مطابقة `offer_id` يُرفض التسعير بدل السقوط على
   `offers[0]` (سعر/غرفة مختلف).

## نقاط ما زالت تمنع اعتماد Production النهائي

1. لم يتم تشغيل Registry حقيقي لـOdoo 19 لأن بيئة البناء لا تحتوي على Odoo.
2. لم تُنفذ Migration على نسخة PostgreSQL فعلية من قاعدة بياناتكم.
3. لم تُختبر بيانات Amadeus الحقيقية أو consolidator أو إصدار أرقام التذاكر.
4. خيار البطاقة المستضافة معطل حتى تركيب Payment Adapter متوافق مع PCI وCallback موقّع.
5. الطلب الخارجي يتم داخل معاملة Odoo؛ قد ينجح الطلب خارجيًا ثم يفشل Commit المحلي في حالة نادرة. الحل الإنتاجي الكامل هو Queue/Outbox + reconciliation worker أو polling.
6. Public Search يحتاج Rate Limiting على مستوى Proxy/WAF؛ حماية Session وحدها ليست كافية ضد إساءة استخدام موزعة.
7. واجهات Figma الأساسية موجودة، لكن لم يتم إكمال كل Frame وحالة Mobile وHotels/Cars/Deals بدقة Pixel-by-Pixel.

## بوابة اعتماد قبل الإطلاق

لا يتم الإطلاق إلا بعد نجاح الآتي:

- Upgrade على نسخة Staging من قاعدة البيانات والـfilestore.
- تثبيت الموديول دون أخطاء Registry أو View أو Constraint.
- اختبار الصلاحيات بكل دور وكل شركة.
- اختبار Issue/Exchange/Refund/Void والفواتير والقيود والتسويات.
- اختبار بحث/تسعير/حجز Amadeus في Test مع حالات النجاح والرفض والـTimeout.
- اختبار reconciliation للحجوزات التي تدخل `Needs Review`.
- اختبار تحميل متزامن للمحفظة والبحث.
- مراجعة Figma على Desktop وMobile.
